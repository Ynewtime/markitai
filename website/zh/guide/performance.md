# 转换性能

URL 提取本地优先：短文和中日韩正文通常在 static 策略内就能完成，不必启动
浏览器。本地文件转换只加载该格式需要的后端：普通 Office 文档走专用路径，
复杂内容、公式和含歧义的表格值保留回退读取器。完整的策略级联见
[抓取策略](./fetch-policy)。

## 实测结果（2026-09-14）

在 macOS、Python 3.12.14 环境下，相对冻结的优化前源码快照，综合提速
**6.01×**：

| 等权负载 | 提速 |
| --- | ---: |
| 通过本地回环 HTTP 获取的五个 URL 页面 | 5.83× |
| DOCX、XLSX、PPTX、PDF 的冷 CLI 转换 | 5.61× |
| 30 个 TXT/HTML/DOCX 文件的批处理 | 6.64× |

综合值是三组的几何平均，覆盖 49 个固定样例、每个样例三个新进程，并关闭模型
增强、远程抓取和缓存。该次审计也比对了产物：40 项转换器/API 快照、23 个
复杂表格样例和 208 个网页样例的输出完全一致。

这是冷启动 CLI 的聚合结果，别拿它当某个具体文档或机器的保证值。URL 计时走本地
回环 HTTP，不含公网时延和远端服务的缓存。冻结的基线已包含 Fake-IP 与中日韩
修复，因此这不算与某个已发布版本的对比。

完整记录见
[`2026-09-14.json`](https://github.com/Ynewtime/markitai/blob/main/scripts/benchmarks/results/2026-09-14.json)，
复现命令见[基准指南](https://github.com/Ynewtime/markitai/blob/main/scripts/benchmarks/README.md)。

## PDF 提取、LLM 批处理与网页工作台（2026-09-25）

PDF 的文字要经过版面模型分析，这是转换中最耗时的步骤之一。CLI、`markitai serve`
和 MCP 服务器会把 12 页及以上的 PDF，以及同时转换的多个 PDF，交给工作进程按页提取，
每个进程单线程运行模型，输出与整篇一次提取完全一致。每页所用的 CPU 时间约为原来的
三分之一，每个工作进程约占 450 MB 内存。工作进程数由 `MARKITAI_PDF_WORKERS` 设置
（默认取 CPU 核数减二，最多 12 个，并且合计不超过可用内存的四分之一），`0` 或 `1`
表示在本进程内提取。Python 脚本可以通过
[`enable_worker_processes()`](./python-api#并行提取-pdf) 启用。

LLM 批处理中，文件转换完成后，在等待模型期间就把转换名额让给下一个文件，转换和增强
因此重叠进行。

在 18 核 Mac 上与 1.1.0 对比冷启动的 CLI 运行，交替各跑三次取中位数，缓存关闭：

| 工作负载 | 1.1.0 | 1.2.0 | 提速 |
| --- | ---: | ---: | ---: |
| 一个 300 页的纯文本 PDF | 16.6 秒 | 4.0 秒 | 4.1× |
| 40 个 PDF（每个 5 页） | 12.1 秒 | 2.9 秒 | 4.1× |
| 240 个混合文件（PDF、DOCX、PPTX、XLSX、HTML、CSV） | 12.9 秒 | 3.9 秒 | 3.3× |
| 30 个文档，`--llm --alt`，模型延迟 0.5 秒 | 7.0 秒 | 4.7 秒 | 1.5× |

`markitai serve` 使用同一套流程。每个任务现在最多 1000 个条目，240 个混合文件
可以放进一个任务（1.1.0 需要拆成五个）：12.8 秒 → 4.0 秒。30 个文档使用
`standard` 预设：6.2 秒 → 3.7 秒。转换 300 页 PDF 期间，API 响应时间的 95 分位
从 295 毫秒降到 3 毫秒。

单个小文件、OCR 和 URL 批处理的耗时与之前相同。核数和页数越多，提速越明显；单独转换的
小 PDF 仍在本进程内提取，因为启动工作进程的开销比省下的时间还多。

## 扫描版 PDF 的 OCR（2026-10-15）

OCR 识别一页扫描件分两步：检测器找出文字行，识别器读出文字。识别器占 80%
以上的时间，而把一页的识别铺到多个核上收益很小。因此 CLI、`markitai serve`
和 MCP 服务器在提取 PDF 页面所用的同一批工作进程里识别扫描版 PDF 的页面，
每个进程一页：每个工作进程只加载一次 OCR 模型，并在分给它的核上运行。
同时进行的页数不超过工作进程数和内存允许的数量（可用内存的一半，每页约
400 MB），所以长扫描件不会让其他文档一直等待。识别出的文字与在单个进程里
识别完全相同。工作进程数同样由 `MARKITAI_PDF_WORKERS` 设置。

一本虚构的 490 页扫描书（中文夹杂英文和代码，六个空白页），
`--preset minimal --ocr`，18 核机器同时被其他任务占用（负载 18 到 42）：

| 运行方式 | 之前 | 现在 |
| --- | ---: | ---: |
| 工作台任务 | 497 秒 | 294 秒 |
| CLI | 510 秒 | 288 秒 |
| CLI 的 CPU 时间 | 6655 秒 | 约 2600 秒 |
| 内存 | 2.1 GB | 约 6 GB（12 个工作进程） |

工作台任务的结果还包含一处 Markdown 清理的修复：它在转换完成的书上花了
50 秒，期间服务器无法响应。页面以 150 dpi 渲染：120 和 200 dpi 对这些虚构
页面的识别并不更好，而分辨率只影响检测器这一步，它在每页中只占一小部分。

## PDF 提取用上所有核（2026-10-20）

PDF 工作进程原来是 CPU 核数减二，把核留给主进程，而工作进程提取时主进程只是
等待。4 核的机器只用两个核提取长 PDF。现在每个本进程可用的核一个工作进程，
仍然最多 12 个，合计不超过可用内存的四分之一。文档以每任务四页交给工作进程，
同一时刻每个工作进程一个任务、外加一个排队，所以同时转换的 PDF（工作台的另一个
任务、批处理的下一个文件）只需等一个任务，而不是整篇文档。页面截图在工作进程
运行时由它们渲染：PyMuPDF 渲染时持有 Python 的 GIL，主进程里的线程只能一次渲染
一页。输出逐字节相同。

虚构的 PDF，冷启动 CLI，4 核 Linux 机器同时有其他任务（交替运行；第一行以提高的
优先级运行，其他任务只占用很少的 CPU）：

| 工作负载 | 之前 | 现在 |
| --- | ---: | ---: |
| 409 页文字 PDF | 53–55 秒 | 29–32 秒 |
| 它的 CPU 时间 | 约 100 秒 | 约 103 秒 |
| 它的峰值内存（所有进程，PSS） | 0.8 GB | 1.3 GB |
| 在它开始 3 秒后启动的 5 页 PDF | 55–65 秒 | 1.4–4.7 秒 |
| 166 页带图片的 PDF，`--screenshot`：主进程 CPU | 6.3 秒 | 1.0 秒 |

在单个进程里、onnxruntime 把每页分摊到所有核时，同样的 409 页需要 101 秒、
276 秒 CPU 时间。14 核及以上的机器原本就有 12 个工作进程，不受影响。

## 排查慢速转换

`-v` 会打印选中的策略和每次回退的原因。`--no-cache` 关闭的是 markitai 自己的
缓存，够不到远端服务的缓存，所以拿已经预热的远端读取器和刚启动的本地 CLI
进程比较，衡量的是不同的工作量。只测量本地转换时用
`--preset minimal --no-remote-fetch`；评估实际使用的完整工作流时，保留平时
开启的模型增强与 OCR 选项。
